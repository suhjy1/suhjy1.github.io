How Look-Ahead Sneaks into Fast Code

Two engineering lessons from the stat-arb project: measure a C++ port against a fair baseline, not against the slowest Python, and give every place the future can leak in its own test.

Part 1. The C++ port, against a fair baseline

A profiled year of the strategy took 11 seconds. The backtest, which I expected to be slow, took 2% of that. More than half went to fitting the Ornstein–Uhlenbeck (OU) model: about 69,000 calls of NumPy's general least-squares routine on 60×2 matrices, plus pulling each stock's column out of a pandas frame. Each fit is just the regression Xt+1=a+bXt+ηX_{t+1} = a + bX_t + \etaXt+1​=a+bXt​+η on 60 points.

I ported the OU fit and the backtest to C++20 with pybind11 and reported 48× and 34× speed-ups. Those numbers were true, but the comparison was weak. The Python side was a loop of tiny library calls, so the ratio mostly measured Python call overhead, not C++. The fair baseline is the same fit done for every stock at once, in closed form:

The honest reading: for the OU fit, the lesson is "batch it", not "write C++". Vectorizing gets most of the gain. C++ is about 2× faster than vectorized NumPy, Numba is faster than my C++, and once pandas conversion is included the C++ call is slower than the NumPy one.

The case for compiled code is stronger in the backtest. Each day's weights depend on the previous day's, through drift between rebalances,

wi,t=wi,t−1 (1+ri,t)1+∑jwj,t−1 rj,tw_{i,t} = \frac{w_{i,t-1}\,(1+r_{i,t})}{1+\sum_j w_{j,t-1}\,r_{j,t}}wi,t​=1+∑j​wj,t−1​rj,t​wi,t−1​(1+ri,t​)​

and through the no-trade band, which compares each target with the drifted book, and the execution lag. That state is carried from day to day, so the loop over days can't be vectorized; only the work within a day can. Python pays a fixed overhead per day, and a compiled loop doesn't. I haven't timed a Numba version of the backtest, so I can't say how much of the gap it would close.

Memory layout. Both kernels read row-major arrays, days by stocks, the way NumPy stores them by default. The OU kernel works one stock at a time and walks down the rows, so each step jumps a whole row ahead in memory and lands on a new cache line. Processing a block of stocks per row, or passing the matrix transposed, is the obvious next change; I haven't measured it. The backtest loops over days on the outside and stocks on the inside, so it reads each row contiguously.

Compiler and SIMD. The release build uses -O2 with no architecture flags and no hand-written vector instructions. I make no SIMD claim for either kernel.

The interpreter lock. Both kernels release Python's global interpreter lock, so threads can split the stocks between them. On 40,000 paths, one thread took 7.65 ms and two threads 4.24 ms, 1.8× on two cores. The original benchmark ran on one thread, so it never showed this.

Parity first. The Python code stayed as the specification. Tolerances were fixed before porting and never relaxed: 10⁻⁸ for OU parameters and 10⁻¹² for every backtest output. Missing-value masks are compared separately from values, because "both returned nothing" and "one returned zero" are different answers. A full strategy run with the C++ engine swapped in matches the Python run, and the native tests pass under AddressSanitizer and UndefinedBehaviorSanitizer.

Part 2. Four doors the future can come through

Look-ahead is the most common way a backtest lies, and it isn't one bug. In this pipeline it can enter through the data, the model fitting, the execution timing or the training labels. A test for one door says nothing about the others, so each has its own.

1. The data layer. Research code reads data only through one typed interface, and every function has a truncation test: build the data with everything, build it again with everything after a cutoff deleted, and require identical answers up to the cutoff. One test builds the leak on purpose. Back-adjusted prices rescale old prices after every later split or dividend, so they depend on the future; the test shows that leak, and the interface returns total-return prices anchored at the start of the window instead. Bad data is masked forward only: a stock leaves the universe on the issue day, never the day before.

2. The pipeline. Walk-forward evaluation slices one long run into test years, which is only valid if what the pipeline does on day t ignores later rows of its panel. Truncating the data doesn't test that, so a second test runs the full strategy on a panel ending at t and on one ending 120 days later. Targets and calibration records match exactly, and profit and loss matches to within 10⁻¹⁵, the size of floating-point summation order.

3. Execution timing. A signal from day t's close can't trade at that close. The engine keeps three dates apart: the decision at t, the fill at the close of t+1, and the first return on t+2. The forward log enforces the same rule on the clock: a target only counts if it is written after the close and before the next session.

4. Training labels. A label like "what this position earned over the next five days" isn't known for five days. The forecast calibration stores each forecast with the model that made it and scores it only after its whole holding period has passed. The neural policies in a side study only draw training samples whose last outcome falls before the refit date, and every refit writes an audit row with the latest outcome it used.

All of these run in continuous integration on a synthetic 50-stock market with listings, delistings and a split, so no vendor data is needed. Passing tests show that these paths don't use future data. They don't prove that no leak exists anywhere.

What I'd keep from this

  1. Benchmark against the best simple alternative. A speed-up over a loop of library calls measures the loop.
  2. Port the part that carries state. Work that vectorizes doesn't need C++; a day-by-day loop with path dependence might.
  3. Keep the slow version as the specification, and fix the tolerances before porting.
  4. Enumerate the doors. Every place time enters the pipeline needs its own look-ahead test.
